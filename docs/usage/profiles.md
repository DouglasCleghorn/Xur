# Profiles

Create profile opens its editor immediately with a default name such as Profile 1.
The editor contains searchable workload, workstation user and GPU selectors, plus add/remove/save
actions. Names, IDs and API routes are assigned automatically. Selecting the same
recipe and GPU allocation in another profile reuses its workload identity; duplicate
also retains those identities. Unload profile stops all managed workloads and clears the loaded state while retaining saved profiles.
Saving a profile does not change the running set until Load profile is approved.

The Profiles page shows the loaded profile, searchable saved profiles, and running
workloads. Choose **Load profile** beside a saved profile to review its changes.
Choose **Unload profile** in the loaded strip to drain requests and stop the set.
Open a row's **More → Delete profile** to remove its saved definition; unload the
loaded profile before deleting it. Delete never removes downloaded models or
workstation home directories. **More → Duplicate** creates an editable copy with
the same workload identities. These actions remain available on phones; secondary
navigation is under More.

The bundled smoke recipe is SmolLM2 135M CPU chat, using the actual llama.cpp
server. The workload picker also includes Gaming workstation and live upstream
model search, described in `docs/usage/model-catalog.md`. Its first start downloads an immutable engine image and a 145 MB GGUF,
verified against its SHA-256. This small model is an additional recipe; it does
not replace the requested Qwen, Fish or ASR models. No model starts automatically
after installation. The recipe records the model revision, license, image digest
and exact arguments in `catalog/models/smollm2-135m-cpu.json`.

A workload has a stable ID, runtime fingerprint, GPU PCI assignments and an API
route. Names and routes are excluded from the runtime fingerprint. An unchanged
workload retains its container, PID, allocation and active requests. Changed or
removed workloads drain before stopping. Added workloads pass their HTTP health
check before routes are published. GPU assignments are currently exclusive;
shared-memory scheduling is still pending. Gaming workstation starts a native
Plasma session on one selected display GPU. One local station is supported; its
keyboard, mouse and audio are the machine’s local devices. Workstation's User
selector lists existing local desktop accounts, Temporary user, and Add user.
Add user asks for a display name and creates an ordinary local account with a
persistent home under `/var/home`; changing profiles or deleting a saved profile
does not remove it. Steam logins and desktop files follow the selected user.
Accounts with an existing active session must sign out before Xur starts their
station. User identity includes both account name and UID and is rechecked before
applying; selecting another user restarts the station while unchanged model
instances stay running. New temporary sessions use a separate account/home that
is removed after unload and recreated on the next start, including after reboot.
Pre-update workstation profiles keep their original account and runtime
fingerprint, shown as Existing workstation user until an explicit selection.
Steam is available
from the desktop launcher. The desktop remains stopped when no profile requests it.

The same controller stores profile revisions and the action journal in SQLite
under `/var/lib/xur/profiles.db`, using WAL and full synchronous commits. The agent
performs typed Podman operations through its private Unix socket. It persists
workload definitions before container creation, allowing retries to adopt the
same labeled container after an interrupted start. It publishes only loopback
backend ports. Engine images must match the installed catalog exactly.

Profile and workload identities use SQLite INTEGER PRIMARY KEY AUTOINCREMENT
registries. New IDs are generated by the database and never entered in the UI.
Existing string keys remain mapped to their integer registry entries so upgrading
does not change running container identities or old saved plans. The existing JSON
contract carries keys as strings for compatibility. A stale editor revision is
rejected rather than overwriting a newer selection.

The separate gateway keeps requests connected to the route snapshot acquired at
request start. Publishing a new route table is atomic. Draining blocks new
requests for the affected workload and waits up to 60 seconds for existing
requests; a timeout leaves the backend running and the operation resumable.
The UI remains available during image downloads and health checks.

Failed operations show their stage and a Resume button. Completed journal actions
are not repeated. External changes that invalidate an exact Keep instance require
operator recovery. Cancel a failed change to review a new plan against the actual
running state. Cancellation does not undo completed actions or reopen drained
routes; applying the next profile publishes its routes. There is no automatic
rollback or automatic replacement of an unchanged instance. The previous active profile remains displayed until the new
operation completes. After a host reboot, Podman's restart service restarts
containers that were running; the agent restores successfully started native
workstations. Preserving a PID across a host reboot is impossible.

# API

Use the existing authenticated bootstrap API to obtain a bearer token. Installer
mode rejects profile mutations. Browser forms also require the application's
antiforgery token.

- `GET /api/station-users`: eligible persistent local desktop accounts.
- `POST /api/station-users`: create a persistent account with `{"name":"Alex"}`.
  A workstation's optional `user` property is `{"username":"returned-name","uid":returned-uid}`
  or `{"username":"temporary","uid":0,"temporary":true}`. Null retains the legacy
  per-workload account for compatibility; the new editor defaults to Temporary user.
- `GET /api/recipes`: immutable recipes available on this installation.
- `GET /api/profiles`: profiles, active revision, real runtime observation and operation.
- `POST /api/profiles/create`: create an empty profile with a generated integer key
  and default name using `{}`, or duplicate one using `{"copy":"profile-key"}`.
- `POST /api/profiles`: save a Profile JSON document. New profiles use revision 0;
  updates must provide the current revision. Workloads include the exact Recipe
  document returned by `/api/recipes`, `id`, `name`, `gpus` (PCI identities), and `route`.
- `POST /api/profiles/{id}/preview`: return the exact plan, digest and expiration.
- `POST /api/profiles/unload/preview`: preview unloading the currently managed set.
  Approve its returned ID and digest through the same apply endpoint.
- `POST /api/profiles/{id}/delete`: delete an inactive saved profile using
  `{"revision":current-revision}`. Stale revisions and loaded profiles are rejected.
- `POST /api/profiles/apply`: approve `{"id":"plan-id","digest":"plan-digest"}`.
- `POST /api/profiles/resume`: retry the unfinished action.
- `POST /api/profiles/cancel`: cancel a failed change and allow a new preview.
- `GET /api/workloads/{id}/logs`: engine logs.

The OpenAI-compatible base URL for a workload with route `chat` is
`http://<machine>:8080/inference/chat/v1`. Use the bearer token as the client API
key. Both ordinary and streamed responses pass through the stable gateway. For
the bundled recipe the model alias is `smollm2`.

# Verification

`tests/Xur.Profile.Tests` starts actual child HTTP engines and a separate gateway
process. It checks twenty complete A↔B cycles, streaming continuity, route-only
changes, exact approval, observation invalidation, graceful drain, fingerprint
changes, conflicting GPU allocation and SQLite recovery after a start side effect.
Delete/unload checks cover stale approval, deletion while shared instances run,
stream draining, preserved definitions, cleared routes and interrupted-stop recovery.
Those engines are test-only and are excluded from the installed runtime.

The `--podman-smoke` mode executes the bundled llama.cpp image and pinned model
through the production runtime, performs chat requests, switches between one and
two model instances, checks the continuing PID/container identity, and stops both.
Media tests exercise the public authenticated API and browser on the installed OS.

GPU discovery reads real PCI/sysfs/DRM identities. NVIDIA uses nvidia-smi and CDI
UUIDs; AMD/Intel probes require their real kernel devices and observed memory.
There is no fabricated GPU inventory. The current Bazzite NVIDIA host includes
the upstream driver integration. The native workstation uses KWin’s selected DRM device and a dedicated user
slice with device restrictions. Teardown terminates that user’s compositor,
applications and audio services, then checks release. The VM exercises a real
Plasma desktop and animated Vulkan/XWayland window alongside a continuing CPU
model, including restart after reboot. Physical HDMI/audio/USB routing, multiple
independent seats and the reference four-3090 deployments still need work.

## Cancel a profile change

**Cancel change** is available while loading or unloading and after an error. It
records a durable cancellation request and stops dispatching further actions.
An action already claimed (including a download, startup health check, drain or
stop) finishes first. The page shows **Cancelling**, names that action, and keeps
other profile mutations disabled until it finishes. This is cooperative
cancellation at action boundaries; it does not forcibly abort a download or kill
an in-flight engine. A long current action can therefore keep it waiting.

Completed changes remain in place. The page lists them and retains any error from
the current action. Already-started workloads remain visible for inspection;
unchanged processes, allocations, routes and active requests are preserved. A
partial cancellation clears the loaded-profile label, allowing the next preview
to reconcile against actual running workloads. If final route publication already
completed when cancellation arrived, the transition completes normally.

Cancellation survives manager restart and is idempotent for the same operation.
The authenticated API is `POST /api/profiles/cancel` with JSON
`{"id":"<current operation ID>"}`; the browser form also binds that ID. An old tab
cannot cancel a newer profile change. Cancelled operations cannot be resumed;
load a profile again to generate a fresh plan.
